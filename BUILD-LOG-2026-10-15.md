## Tier 1 — launch-critical

### 1.1 One staff email per form lead

- `lib/held-notification.ts` — the rules: when to hold, the atomic claim,
  release, retry, give-up, and what a page-two save does. Pure; the store and
  sender are injected.
- `lib/held-notification-store.ts` — Supabase store + the sender (the
  existing `sendLeadNotification`, with the row's recorded recipients and
  "Received" = the request's own `created_at`).
- `lib/release-job.ts` + `app/api/cron/release-held-leads` (every minute) +
  `app/api/cron/lead-backstop` (daily, 13:00 UTC) + `vercel.json`.
- `app/api/consultation/[id]/release` — "Skip for now" (and a Save with
  nothing filled in) sends the held email at once.
- `app/api/consultation/route.ts` — step one holds a form lead's staff email
  instead of sending it; platform copy starts first and is never waited on;
  visitor confirmation and text unchanged; an after-response sweep.
- `app/api/consultation/[id]/route.ts` — page-two save: held → sends ONE
  email with the details; already sent → the existing threaded "Details
  added"; mid-send → waits, then the update.
- `components/ContactForm.tsx` — Skip calls the release endpoint
  (fire-and-forget, `keepalive`), then shows the confirmation as before.
- `supabase/migrations/0009_held_notification.sql` — hold columns, a
  `notify_failures` log on the row, `lead_job_heartbeats`. **Not applied.**
- Unit tests `lib/held-notification.test.mjs`: save path, skip path, 2-minute
  timeout, late page-two save, page-two during an in-flight send (sent / and
  failed), failed-send retry with the failure log, give-up after 24 h, no
  double send (Skip + save + job racing), stale claim, cron-not-configured
  fallback (secret unset, no heartbeat, stale heartbeat, daily-only cadence,
  unreadable), env scoping, the endpoint's 503/401.

Decisions:
- **Fail-safe is a heartbeat, not just the secret (Ben asked for this).** Step
  one holds only when `CRON_SECRET` is set AND this deployment's release job
  ran in the last 150 s AND the run before that was within 150 s of it. Any
  failure to show that → send at step one, with the reason in the log.
- **Hold state lives in its own column (`notify_hold_state`) (my call)**,
  so `notify_status` keeps meaning what it meant (sent/failed/not_configured)
  and the existing "Details added" logic reads it unchanged.
- **Rows are scoped to the deployment that held them (`notify_hold_env` =
  `VERCEL_ENV`, "local" off Vercel) (my call)** so a local test server's job
  can never send — or mark as sent — a real production lead.
- **Spam-trap leads are never held (my call)**: the row does not store the
  trap, so a later send could not show the spam warning; bots never reach
  page two anyway.
- **Retries stop after 24 h (my call)**, marked `gave_up` and logged as an
  error naming the lead.
- **A claim older than 2 min is re-claimable (my call)** — a sender that died
  mid-send. The one way a duplicate is possible; preferred over a lost lead.
- **Unhandled ordering case closed:** if a send is claimed in the instant
  between a page-two save and its state read, that email already has the
  details, so no "Details added" follows (`notify_had_details`).
- **The PATCH reads the hold state in a separate query (my call)** so a
  database without 0009 answers "not held" instead of failing the save.
